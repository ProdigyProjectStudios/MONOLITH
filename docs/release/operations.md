# Monitoring and data lifecycle

## Request and job telemetry

Access events contain a generated request ID, trace ID, route template, HTTP method, status and elapsed milliseconds. The API returns the request ID as a response header. Headers, business records, OAuth parameters and bearer values are excluded. Optional OTLP/HTTP export uses the collector configured through `OTEL_EXPORTER_OTLP_ENDPOINT`. Set it on both API and worker. RQ metadata carries a W3C trace parent and tenant routing information. Trace export runs separately from request handling. On shutdown the API flushes the batch processor. Worker subprocesses flush job spans before exit.

Use an administrator identity for `GET /api/operations/metrics`. Its HTTP counters and cumulative duration buckets cover that tenant in the current API process since startup. Database counts, investigation statuses and model-call receipt counts come from persisted records. Queue depth and worker heartbeat describe shared infrastructure capacity. Missing response receipts and unavailable metering remain explicit in the Studio. Readiness checks query the database schema and Redis/RQ. Liveness is `/api/health`. Staging and production expect `/api/health/ready` to return 503 when the worker or a required dependency is unavailable.

Authenticated requests share a per-actor fixed-minute limit through Redis. Unrecognized credentials use a separate client-address bucket. The response includes HTTP 429 and Retry-After. A limiter dependency failure returns 503. Single-process development without Redis can use an in-memory limit. Apply an ingress traffic policy suitable for the public host as well. Set `MONOLITH_RATE_LIMIT_PER_MINUTE` to a positive integer for production.

## Alerts

Run `python deploy/health_watch.py --state /var/lib/monolith-watch/status.json` from a machine independent of the application. Set `MONOLITH_API_URL` and `MONOLITH_MONITOR_TOKEN_FILE` there. Set `MONOLITH_ALERT_WEBHOOK` to your operator-managed HTTPS receiver to deliver state transitions. Treat the webhook URL as a secret. The process polls once per minute, emits a structured event, and only sends changed conditions. A recovered service generates a healthy transition. Thresholds are a queue depth of 100 or a server-error proportion of at least 5% when at least 10 tenant requests occurred since the previous sample. Unreachable readiness or metrics also raises an alert. Run `--once` for an external scheduler; exit codes 0, 2 and 3 mean healthy, alert and notification failure. An external incident destination needs separate operator provisioning.

## Export, retention and erasure

An admin can page through `GET /api/operations/export?limit=100` using the returned opaque cursor. The export includes canonical sources, documents, events, investigation inputs, evidence, receipts, decisions and graph history. Operational locks, OAuth credentials and connector tokens are excluded. `GET /api/operations/audit?after=0&limit=100` exports the audit timeline. Archive a consistent point-in-time copy using the backup workflow if ingestion remains active during a long export.

The API prunes audit entries older than `MONOLITH_AUDIT_RETENTION_DAYS` at startup and daily. Evidence and decision history remain available until workspace erasure; removing those independently would break citations. For manual retention, run `python -m monolith.lifecycle prune-audit --days 90 --tenant TENANT` in the backend image.

For a workspace deletion, revoke the HubSpot grant, remove its identities from all secret mappings, and stop every API and worker writer. Keep PostgreSQL and Redis running. From an administrator-controlled, one-off backend container using the same database and Redis configuration, run `python -m monolith.lifecycle erase TENANT` to preview the row count. Repeat with `--confirm TENANT` to erase that tenant's evidence, audit, vectors, queued and retained jobs, and encrypted connector state. The operation can be retried after interruption. A tombstone prevents automatic Northstar reseeding. Restart the services with the deprovisioned credential configuration. For erasure on a single-tenant installation supply a valid separate maintenance identity or run the offline command with development identity validation and empty credential mappings; keep network ingress closed.

Backups and remote telemetry have independent retention policies. Restrict and expire backup copies according to the agreed retention period. After restoring an older backup, reapply subsequent erasures before enabling ingress. Customer or operator downloads, external CRM records and isolated browser showcase sessions have separate owners. Production mode authenticates to the same-origin API and keeps business records in memory in the browser.
